В Go методы – это функции со специальным аргументом, называемым **получателем (receiver)**. С точки зрения компилятора, метод – это просто функция, где получатель выступает в роли первого, неявного аргумента.

```go
// То, что мы пишем:
func (u User) Greet() string { ... }

// То, что видит компилятор (концептуально):
func User_Greet(u User) string { ... }
```

Получатель может быть двух типов: **по значению** (value receiver) и **по указателю** (pointer receiver). Выбор между ними является одним из важнейших архитектурных решений при проектировании API в Go.

```go
type User struct {
    Name string
    Age  int
}

// Получатель по значению (работает с копией)
func (u User) Greet() string {
    return fmt.Sprintf("Здравствуйте, %s.", u.Name)
}

// Получатель по указателю (работает с оригиналом)
func (u *User) SetAge(newAge int) {
    u.Age = newAge // Эквивалентно (*u).Age = newAge
}
```

#### 1. Семантика получателей: Когда что использовать?

Выбор между `T` и `*T` не должен быть случайным. Сообщество Go выработало строгие правила (так называемые "Golden Rules"):

**Используйте указатель (`*T`), если:**
1. **Метод изменяет состояние объекта.** Если вам нужно модифицировать поля структуры, получатель обязан быть указателем. Иначе вы измените лишь временную копию, которая будет уничтожена после выхода из метода.
2. **Структура содержит `sync.Mutex` или другие примитивы синхронизации.** Мьютексы категорически запрещено копировать. Если вы используете value-приемник, структура скопируется вместе с мьютексом, что приведет к состоянию гонки (data race) и фатальным ошибкам блокировок.
3. **Структура велика.** Передача большой структуры по значению требует дорогостоящего копирования памяти. Указатель всегда занимает 8 байт (на 64-битных системах).

**Используйте значение (`T`), если:**
1. **Тип является примитивным или псевдонимом базового типа** (например, `type MyInt int` или небольшие структуры вроде `time.Time`, `complex128`). Их копирование дешевле, чем разыменование указателя.
2. **Структура представляет собой неизменяемые данные (Immutable).** Если метод только читает данные, а структура небольшая, value-приемник подчеркивает безопасность и отсутствие побочных эффектов.

*Эмпирическое правило (Rule of thumb):* Если вы сомневаетесь, используйте указатель (`*T`). Это обеспечивает консистентность и избавляет от трудноуловимых багов, связанных с потерей изменений.

#### 2. Множества методов (Method Sets) и Интерфейсы

Это самая сложная и важная концепция, связанная с методами. **Множество методов** определяет, какие интерфейсы может реализовывать тип.

* Множество методов типа `T` состоит из всех методов с получателем `T`.
* Множество методов типа `*T` состоит из всех методов с получателем `T` **И** всех методов с получателем `*T`.

**Почему это критически важно?**
Если интерфейс требует метод с pointer-приемателем, то тип-значение `T` **не реализует** этот интерфейс, даже если компилятор иногда позволяет вызывать этот метод на значении (автоматически беря адрес).

```go
type Saver interface {
    Save() error // Допустим, этот метод имеет receiver *User
}

func (u *User) Save() error { /* ... */ }

func doSave(s Saver) { /* ... */ }

func main() {
    u := &User{}
    doSave(u) // Работает: *User реализует Saver
    
    v := User{}
    doSave(v) // ОШИБКА КОМПИЛЯЦИИ! User не реализует Saver, 
              // так как в его множестве методов нет Save().
              
    doSave(&v) // Работает
}
```
*Исключение:* Если переменная неадресуема (например, возвращаемое значение функции `getUser().Save()`), компилятор не сможет неявно взять адрес, и вызов метода с pointer-приемателем на значении приведет к ошибке компиляции.

#### 3. Вызов методов на `nil`-указателях

В языках вроде Java или C# вызов метода на `null`-объекте гарантированно выбрасывает `NullPointerException`. В Go получатель – это просто аргумент функции. Если аргумент равен `nil`, функция всё равно вызовется!

Это позволяет создавать **nil-safe** методы, которые элегантно обрабатывают отсутствие объекта без необходимости проверок `if obj != nil` перед каждым вызовом.

```go
type Config struct {
    Timeout int
}

// Метод безопасен для вызова на nil
func (c *Config) GetTimeout() int {
    if c == nil {
        return 30 // Значение по умолчанию
    }
    return c.Timeout
}

func main() {
    var cfg *Config // cfg == nil
    fmt.Println(cfg.GetTimeout()) // Выведет 30, паники не будет!
}
```
*Примечание:* Стандартная библиотека Go активно использует этот паттерн (например, метод `String()` у `*bytes.Buffer` или `*os.File`).

#### 4. Композиция и продвижение методов (Method Promotion)

В Go нет классического наследования. Вместо этого используется **встраивание (embedding)**. Когда одна структура встраивается в другую, методы внутренней структуры «продвигаются» (promote) на уровень внешней.

```go
type Base struct{}
func (b Base) ID() int { return 1 }

type Admin struct {
    Base // Встраивание (анонимное поле)
    Role string
}

func main() {
    a := Admin{}
    // Мы можем вызвать метод Base напрямую на Admin
    fmt.Println(a.ID()) 
    
    // Под капотом это транслируется в: a.Base.ID()
}
```
Если во внешней структуре объявить метод с таким же именем, он **переопределит** (shadow) метод внутренней структуры, что позволяет легко реализовывать паттерн декоратора или переопределять поведение.

#### 5. Подводный камень: Смешивание получателей

Строгое правило Go-этикета: **Никогда не смешивайте value и pointer receivers для одного и того же типа**, если на то нет веских причин (например, специфические требования к производительности в горячем цикле).

```go
// ПЛОХО: путаница для разработчика и компилятора
func (u *User) Update() { ... }
func (u User) Print() { ... } 
```
Если хотя бы один метод структуры требует изменения состояния (и, следовательно, pointer-приематель), **все** остальные методы этой структуры также должны использовать pointer-приематель. Это делает API предсказуемым и гарантирует корректную работу с интерфейсами.

2. **Безопасность памяти:** Почему использование value-приемателя для структуры, содержащей `sync.Mutex`, является фатальной ошибкой проектирования? Что именно произойдет при вызове такого метода?
3. **Множества методов:** Тип `T` имеет метод `Foo()`. Тип `*T` имеет методы `Foo()` и `Bar()`. Интерфейс `I` требует наличия метода `Bar()`. Может ли переменная типа `T` (не указатель) быть передана в функцию, ожидающую интерфейс `I`? Почему?

```go
type Counter struct {
    Count int
}

func (c Counter) IncrementValue() {
    c.Count++
}

func (c *Counter) IncrementPointer() {
    c.Count++
}

func main() {

    c1.IncrementValue()
    fmt.Println("c1:", c1.Count)
```

#### Упражнение 2: Ловушка интерфейсов (Найти и исправить ошибку)

```go
type Writer interface {
```

#### Упражнение 3: Потокобезопасный кэш (Работа с Mutex)
Ниже представлен код кэша. В нем допущена критическая архитектурная ошибка, связанная с типом получателя, которая приведет к состоянию гонки (race condition) или панике при использовании в горутинах. Найдите ошибку и исправьте её.

```go
type Cache struct {
    mu   sync.Mutex
    data map[string]string
}

func (c Cache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = value
}

func (c Cache) Get(key string) (string, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    val, ok := c.data[key]
    return val, ok
}
```
